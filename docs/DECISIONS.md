# Decisions

Project-level decisions. Add new entries at the top. Change the status instead of
deleting an entry.

| Date | Decision | Reason | Status |
|---|---|---|---|
| 2026-10-03 | **Player collision works in tile coordinates.** The tile of a position in 1/32 px is its high byte (`LEFT_COLUMN`, `FEET_ROW`, `head_row` in `player.c`), and `column_has` walks one collision ring column with a pointer. `player_update` no longer takes the level; it reads `current_level`. | `player_update` went from about 44 to about 24 lines per frame, and bank 0 got 752 bytes back. Same results: `tools/physics.py` has the same helpers, and the frame-by-frame test passes. Reading the global `player` instead of a pointer was tried too: 2 lines faster, not worth a different API. | Accepted |
| 2026-10-03 | **`head_row` is a function, not a macro.** SDCC in GBDK 4.5.0 compiles `y < 992 ? 0 : (uint8_t)((y - 992) >> 8)` to 0 on both branches when it is passed straight as a function argument; in a local variable or a `return` it is right. | Found when the frame-by-frame physics test failed; a 10-line file reproduces it. When a change misbehaves for no visible reason, read the compiler's output in `obj/*.asm`. | Accepted |
| 2026-10-03 | **The ROM counts lag frames** (`lag_frames`: every VBlank that passes during a gameplay update, from GBDK's `sys_time`). **The tests allow an update to end at most 140 lines after VBlank starts**, of 154, timed over a scripted route through the greybox level in both modes. | The counter also works in Emulicious. The line count shows how close a frame is to lagging before it does. The 14-line margin covers PyBoy's timing, which is close to the hardware's but not exact; M3 still adds entities and parallax, M6 music. | Accepted (owner, 2026-10-03) |
| 2026-10-03 | **The reachability check runs a frame-exact Python copy of the player physics** (`tools/physics.py`), compared with the ROM frame by frame in the tests. Its model: gates open, no going back past a gate, enemies ignored, pickups on fatal jumps don't count, a running start possible anywhere. | Jump arcs and reachability are only useful if they match the real jump. A copy that drifts from `player.c` fails the tests. | Accepted |
| 2026-10-03 | **The ceiling-corner slide is computed from the head row** instead of trying 8 shifted positions: if only the tile at one end of the head row is solid and the body reaches into it by at most 4 px, slide out of it, if the body fits there. | Same results, but the old search cost about 55 scanlines and made every head bump under a ceiling a lag frame (bug 18). | Accepted |
| 2026-10-03 | **Greybox level: the fragment under platform A moved to column 26.** | The first reachability check found it unreachable: platform A is at body height, so nothing fits under it. The old walk-through physics hid this. | Accepted |
| 2026-10-03 | **Ground bot removed from the start of the greybox level** (the old level 1 bot patrolling x 64–112). | Owner's request: it was too hard to get past at the start. | Accepted |
| 2026-10-03 | **Streaming works in both directions.** The column entering the view is drawn on whichever side it enters; a jump of more than a screen redraws the whole view. | The player can walk back left within a section; the gate lock only stops the camera at an opened gate. LEVEL_PIPELINE.md said streaming would only run to the right, which was wrong. | Accepted |
| 2026-10-03 | **Columns are drawn with `set_bkg_tiles` from a 13-byte column buffer, not `set_bkg_submap`.** | `set_bkg_submap` uses the same coordinates for the map and the screen, and our map starts at screen row 3. The buffer is also where fragments are put in and collision is looked up. Deviates from the plan of 2026-10-02. | Accepted |
| 2026-10-03 | **The tileset's collision table and the fragment positions are copied to WRAM at level load** (256 + 64 bytes). The collision lookup is a macro. | The first version of streaming missed VBlank on every column draw (a lag frame): it searched the banked entity list and switched banks per column. Measured with PyBoy: a normal frame now ends near line 88 of 154, a frame that draws a column near line 125. `player_update` alone takes about 45 lines; M3's frame budget work starts there. A `static inline` function in a header breaks the build with SDCC's `-debug` symbols, hence the macro. | Accepted |
| 2026-10-03 | **Camera: focus = player + look-ahead, kept within 8 px of screen x 80; the look-ahead eases 1 px per frame to 24 px in the running direction and flips after 16 px of running the other way.** A respawn puts the camera on the player at once. | Values from RESEARCH.md 2.2. The camera never moves more than 1 px per frame faster than the player. The gate lock waits for the gates (M3). | Accepted (tune in playtesting) |
| 2026-10-03 | **A test room ships in the ROM** (`levels/test_jumps.tmj`, index `LEVEL_TEST_JUMPS`), chosen by writing `level_index` before a reload. | The jump metric tests need fixed walls and pits; writing collision from a test no longer works once columns stream. About 2 KB in a ROM bank. M3's level-select cheat can use the same index; M9 decides whether test rooms stay in the release. | Accepted |
| 2026-10-03 | **Level data format** (`src/level/level_data.h`): entities in world pixels, sorted by x, with the section starts and player start in the level header. Enemies are rectangles whose width is the patrol range; all other entities are tile objects using the tileset's marker tiles. Each tileset's collision table has one byte per tile instead of 256. The GBC attribute map waits for M4. | Tile objects show an icon in Tiled and snap to the grid; the converter checks the grid. A table sized to the tileset wastes no ROM, and the converter rejects tile ids outside it. | Accepted |
| 2026-10-03 | **The greybox test level starts with level 1's exact layout** (columns 0–31), then adds a pit, a one-way shelf, spikes, gates, steps and the exit (columns 32–55). | When the game switches to loading Tiled levels (M2 step 4), the tests written for level 1 keep their meaning. | Accepted |
| 2026-10-03 | **The greybox tileset is drawn by a script** (`tools/greybox_tileset.py`), which also writes its Tiled `.tsx` with each tile's class and collision. | Placeholder tiles stay reproducible and consistent with their collision. The M5 art tilesets get hand-made `.tsx` files instead. | Accepted |
| 2026-10-03 | **Jump metrics are measured in the ROM and pinned by tests** (`tests/test_jump_metrics.py`, LEVEL_DESIGN.md section 4). Gaps count from a takeoff on the ledge, without coyote time; a landing counts with 1 px of the body on the far ledge. Level 1's main path: steps up to 2 tiles, gaps up to 5. | Layouts are built on these numbers, so a physics change must not move them unnoticed. The level 1 limits apply the difficulty rule (2 tiles below the maximum) to the standing jump, so every jump also works from a standstill. | Accepted |
| 2026-10-03 | **Strong gravity on every fall.** Light gravity (0.125 px/f²) only while rising with A held; strong gravity (0.375) when falling, even with A held, and right after A is released (jump cut). Near the top of a held jump, gravity is halved (apex hang). | As in Super Mario Bros.: the fall is snappier than the rise, and a held A doesn't turn into a slow float down. Claude's default; the owner said go ahead without choosing. | Accepted (tune in playtesting) |
| 2026-10-03 | **Velocities are `int8_t` in 1/32 px per frame** (at most ±3.97 px/f). | 8-bit math is cheaper on the Game Boy CPU, and every value in RESEARCH.md 2.2 fits. A jump faster than 3.97 px/f would need `int16_t`. | Accepted |
| 2026-10-03 | **Hazard tiles cost a life like an enemy does, and invincibility protects from both.** Falling out of the level still costs a life while invincible. | One rule for every hit is easier to learn and to explain. | Accepted (Claude's proposal) |
| 2026-10-03 | **Coyote time and jump buffer count down only after they are checked**, so `COYOTE_FRAMES 6` means a jump works on each of the 6 frames after the feet leave a ledge, and `JUMP_BUFFER_FRAMES 5` keeps a press for the press frame plus 4. | The number in `player.h` is the number the player gets. Found when the first version gave only 5 coyote frames. | Accepted |
| 2026-10-03 | **Code style: self-explanatory and short.** Clear names, one short comment per function saying what it handles, brief walk-through comments only where needed, no long explanations in code. | The owner walks through the code to understand and explain it. Rules in CLAUDE.md. | Accepted |
| 2026-10-03 | **Invincibility after losing a life: 1.5 s** (90 frames). | Owner's choice; closes bug 12. | Accepted |
| 2026-10-03 | **Vision: a cozy little game** that looks good, has solid logic, runs on real DMG and GBC hardware, and that the owner can explain end to end. | The owner's goal for the revival: learn C and make a Game Boy game they love. It guides trade-offs: forgiving rules, readable visuals, simple code over clever code. | Accepted |
| 2026-10-03 | **Documentation: a running record now, the full explainer at the end.** DECISIONS.md (what and why) and SOURCES.md (where each idea and asset came from, where it's used) are kept current. The final "how it works" document is written from them in M9. | Owner's choice: one good document when the game is done, built from records that can be reused. | Accepted |
| 2026-10-03 | **No copied assets in the final game.** No Mario, mushrooms or other copied art; every asset is original (owner or Claude Design) or openly licensed and credited. The list of what must be replaced is in SOURCES.md. | Owner's choice. It also keeps the game legal to share. | Accepted |
| 2026-10-03 | **The player stays a 16×32 metasprite** (4 hardware sprites in 8×16 mode). | Owner's early decision, kept. A hardware sprite is at most 8×16 px, so any bigger character is several sprites; 2 per screen line leaves room for enemies. | Accepted |
| 2026-10-03 | **Parallax: a 3-row band at the top of the screen** scrolls slower than the level. It is decoration only: no platforms, enemies or fragments. The level uses rows 3–15 (13 rows); the HUD covers rows 16–17. | Owner likes the effect from Larold's tutorial. 3 rows give depth and leave room for the 4-tile-tall player. | Accepted |
| 2026-10-03 | **Fade in and out between screens and on level load stays**: `BGP_REG` steps on DMG, palette steps on GBC (palette module, M4). | Owner likes it; it was in the early versions. | Accepted |
| 2026-10-03 | **Lives: 3. Losing a life returns to the last opened gate. Game over refills the lives and restarts the current section:** fragments from earlier sections stay, fragments collected since the last gate are reset. | Owner chose "game over → last gate". Resetting the current section's fragments gives game over a cost without sending the player back to the start. | Accepted (section reset rule proposed by Claude; owner may change it) |
| 2026-10-03 | **Claude Design is used for pixel art when needed** (reaffirmed), first for replacing the copied sprites. | Owner's request. | Accepted |
| 2026-10-02 | **Mainframe boss: "KERNEL".** One-screen arena; the boss is drawn with background tiles. Kill-switch terminals light up in turn; hold Up on the lit one to upload a patch. 3 phases reuse the level 3 and 4 mechanics. | Works within the sprite limits, and the player doesn't need an attack. [RESEARCH.md](RESEARCH.md) section 3. | Accepted (concept; details in M8) |
| 2026-10-02 | **Brighter palettes on GBA**, chosen at boot when `_is_GBA` is set. | A GBA shows GBC games darker. Costs one extra palette table per asset. | Accepted |
| 2026-10-02 | **Hard mode after clearing the game:** every gate needs all of its section's fragments. | Cheap replay value: one flag and a menu entry. | Accepted |
| 2026-10-02 | **Story: "PATCH n/5".** Each level's fragments compile into a patch, uploaded in the boss fight. A 3-line boot screen, and one corrupted AI log line per elevator ride. | Gives the fragments a purpose with very little text. | Accepted |
| 2026-10-02 | **Music: Tronimal's Game Boy Music Packs #1 and #2 (CC BY 4.0), sound effects from GBFX/GBFX2 (CC-BY), played with hUGEDriver and untoxa's VGM2GBSFX player.** Needs `CREDITS.md` and an in-game credits screen. | Ready now, fitting tracks, clear license. Any track can still be replaced by the owner's own songs. | Accepted. Replaces the "song source decided later" entry. |
| 2026-10-02 | **The camera locks behind an opened gate.** No going back to earlier sections. | Simpler streaming, spawning and checkpoints, and each gate feels like progress. Missed bonus fragments can be collected on a replay. | Accepted |
| 2026-10-02 | **Positions in 1/32 px** (`uint16_t`), as in the GB Studio engine. | The tile index is the high byte, so tile lookups are cheap. A 160-tile level is 40,960 units, which fits `uint16_t`. | Accepted (Claude's proposal; the owner didn't object) |
| 2026-10-02 | **Collision kept in a 32×16 RAM ring (512 bytes)**, filled from the per-tileset table in ROM while columns stream in. | Opening gates and collecting fragments become single writes, and collision checks never switch ROM banks. Used by BlackCastle, marioland-gbdk and CrossZGB. | Accepted (Claude's proposal; the owner didn't object) |
